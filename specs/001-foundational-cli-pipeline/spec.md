**功能分支 (Feature Branch)**: `001-foundational-cli-pipeline`

**创建日期 (Created)**: 2026-08-05

**状态 (Status)**: 草稿 (Draft)

**输入 (Input)**: 用户描述：「基础链路打通 —— 基础命令行管线：给定代码仓库、基准分支、待发布分支，以及绑定的测试环境执行数据源，产出三色（绿/红/黄）增量覆盖判定报告。仅限命令行（CLI-only）；不含持久化、服务层或前端。（宪法第六篇章迭代 #1，经 /speckit-specify 确认。）」

## 用户场景与测试 / User Scenarios & Testing *(mandatory)*

### 用户故事 1 - 三色增量覆盖报告 (User Story 1, Priority: P1)

作为发布工程师，我希望执行一条命令——给定代码仓库、基准分支、待发布分支，以及绑定的测试环境执行数据源——产出一份三色（绿/红/黄）报告，展示哪些增量代码变更已被真实测试流量执行，以便我在发布前识别并拦截未测试的变更。

**为何此优先级 (Why this priority)**：这是平台的核心价值——把"真实测试是否真的执行了变更代码？"转化为可操作的发布前判定。它单独即可交付一个可用的 MVP，是后续所有迭代的基础。

**独立测试 (Independent Test)**：提供一个已知增量变更集合、已知执行数据状态（部分变更已执行、部分未执行、部分无法匹配）的仓库；执行单条检查命令；验证报告对"完全执行"的变更标绿、"从未执行"的标红、"无法精准匹配"的标黄。

**验收场景 (Acceptance Scenarios)**：

1. **给定 (Given)** 待发布分支有 5 处增量变更——其中 3 处被测试流量完全执行、1 处从未执行、1 处因重构无法匹配——**当 (When)** 工程师执行检查——**那么 (Then)** 报告显示 3 绿、1 红、1 黄。
2. **给定 (Given)** 待发布分支与基准分支完全相同（无增量变更）——**当 (When)** 工程师执行检查——**那么 (Then)** 报告提示零变更（无需校验）。
3. **给定 (Given)** 执行数据并非来自绑定的测试环境，或与待发布分支/版本不匹配——**当 (When)** 工程师执行检查——**那么 (Then)** 系统拒绝该数据、不产出判定，并说明原因。

---

### 用户故事 2 - 执行数据采集控制 (User Story 2, Priority: P2)

作为发布工程师，我希望能从绑定的测试环境服务实例触发一次当前执行数据的新鲜采集（dump）、重置已采集的数据，并跨多轮测试累加执行数据，以便判定结果反映本次发布所运行的完整测试流量集合，而非某一时刻的快照。

**为何此优先级 (Why this priority)**：真实的发布测试往往跨多轮/多次会话。若没有采集控制，工程师无法组装出完整的执行数据以得到准确判定。本故事直接建立在 US1 的报告之上。

**独立测试 (Independent Test)**：在测试环境中运行若干轮测试流量；先重置、再跨轮累加；生成报告；验证判定反映所有已累加的轮次，且重置会清除先前数据。

**验收场景 (Acceptance Scenarios)**：

1. **给定 (Given)** 已存在先前执行数据——**当 (When)** 工程师执行重置——**那么 (Then)** 随后的报告不再反映任何先前数据。
2. **给定 (Given)** 运行了两轮测试流量——**当 (When)** 工程师先累加再报告——**那么 (Then)** 判定反映两轮执行的合并结果。

---

### 用户故事 3 - 确定性、隔离、零侵入运行 (User Story 3, Priority: P3)

作为发布工程师 / 测试负责人，我希望每次检查都可复现（相同输入 → 相同判定）、只接受绑定到正确服务实例/版本的测试环境数据，并且不要求修改业务项目代码，以便判定结果可信、不会跨版本或任务污染、且能在各项目间低成本推广。

**为何此优先级 (Why this priority)**：可信度与可推广性决定判定能否作为真正的发布检查被使用。若没有确定性、环境隔离与零侵入接入，输出就无法被信赖，也无法在项目组合中规模化。

**独立测试 (Independent Test)**：用相同输入把同一检查运行两次并确认判定完全一致；提供来自非测试环境或版本不匹配的执行数据并确认被拒绝；接入一个示例项目并确认无需改动应用代码。

**验收场景 (Acceptance Scenarios)**：

1. **给定 (Given)** 相同的仓库、分支与执行数据——**当 (When)** 检查运行两次——**那么 (Then)** 两次判定完全一致。
2. **给定 (Given)** 一个已接入检查的业务项目——**当 (When)** 执行接入——**那么 (Then)** 未修改任何应用源代码或生产依赖（唯一新增的是一个仅用于测试环境的采集器）。

---

### 边界场景 / Edge Cases

- 两个分支之间无增量变更 → 报告显示零变更。
- 尚未采集任何执行数据 → 每一处增量变更都为红色。
- 分支之间存在大量重构 / 方法签名漂移 → 受影响的变更为黄色（人工复核）。
- 执行数据来自与待发布分支不同的 commit / 版本 → 被拒绝。
- 基准分支与待发布分支无共同祖先 → 给出明确错误。
- 某方法仅被测试流量部分执行 → 按变更行/分支粒度报告，暴露未覆盖的行/分支，并标记为 'partial'（部分）以提醒关注（见 FR-013）。
- 增量变更集合非常大 → 检查仍在交互式目标时长内完成；报告保持完整。

## 需求 / Requirements *(mandatory)*

### 功能需求 / Functional Requirements

- **FR-001**：系统必须（MUST）计算指定仓库中、用户选择的基准分支与待发布分支之间的增量代码变更。
- **FR-002**：系统必须（MUST）为每一处增量变更判定其是否已被真实测试环境流量执行。
- **FR-003**：系统必须（MUST）为每一处"可完整匹配"的增量变更给出唯一一个判定：绿色（完全执行）、红色（从不执行）或黄色（无法精准匹配——需人工复核）。
- **FR-004**：系统必须（MUST）生成一份人类可读的报告，列出每一处增量变更及其判定与位置。
- **FR-005**：系统必须（MUST）能按需从绑定的测试环境服务实例触发一次当前执行数据的新鲜采集（dump）。
- **FR-006**：系统必须（MUST）支持重置已采集的执行数据，并必须（MUST）支持在报告前跨多轮测试累加执行数据。
- **FR-007**：系统必须（MUST）只接受来自绑定到所选待发布分支/构建的测试环境的执行数据；必须拒绝（MUST NOT）来自生产、预发、本地调试环境，或版本/commit 不匹配的数据。
- **FR-008**：系统必须（MUST）在不依赖、不读取、不参考任何单元测试覆盖率数据的情况下计算判定。
- **FR-009**：系统必须（MUST）在不修改业务项目应用源代码或生产依赖的前提下完成接入（唯一新增的是一个仅用于测试环境的执行数据采集器）。
- **FR-010**：系统必须（MUST）对相同输入产出完全一致的判定输出。
- **FR-011**：系统必须（MUST）在给定代码仓库、基准分支、待发布分支与测试环境执行数据源的情况下，通过单次命令行调用完成一次完整检查。
- **FR-012**：系统必须（MUST）按 项目 / 版本 / commit / 测试任务 / 服务实例 隔离执行数据，使不同版本或任务的数据不发生交叉污染。
- **FR-013**：当某处增量变更仅被部分执行时，系统必须（MUST）按变更行/分支粒度报告，暴露具体未覆盖的行/分支，并将该单元标记为 'partial'（部分）以提醒关注。三种判定（绿/红/黄）的含义保持不变；'partial' 是与明细一并呈现的提示性标记，并非对三色标准的修改。

### 关键实体 / Key Entities *(include if feature involves data)*

- **仓库 (Repository)**：受检的代码源，包含基准分支与待发布分支。
- **分支 (Branch，基准 / 待发布)**：基准分支 = 线上稳定版本；待发布分支 = 即将发布上线的发展分支。
- **增量变更 (Incremental Change)**：基准与待发布之间发生变更的一个代码单元（含位置、新增/修改、判定）。
- **执行数据 (Execution Data)**：从绑定的测试环境服务实例采集的真实执行流量，绑定到具体的 版本 / commit / 任务 / 实例。
- **判定 (Verdict，绿 / 红 / 黄)**：对一处增量变更的覆盖判定结论。
- **覆盖报告 (Coverage Report)**：列出增量变更、判定与位置的三色输出。
- **测试环境服务实例 (Test-Environment Service Instance)**：采集执行数据所绑定的目标。

## 成功标准 / Success Criteria *(mandatory)*

### 可度量结果 / Measurable Outcomes

- **SC-001**：发布工程师通过单次调用即可获得完整的三色增量覆盖报告，无需任何强制的中间人工步骤。
- **SC-002**：100% 的增量变更都被归类——绿色、红色、黄色，或（对仅部分执行的单元）标记 'partial' 并附未覆盖明细；没有变更被遗漏未分类。
- **SC-003**：对相同输入重复检查，得到的判定完全一致。
- **SC-004**：每一处从未被测试流量执行的增量变更都被标记为红色，从而能在发布前识别未测试变更。
- **SC-005**：接入一个业务项目，对其应用源代码或生产依赖的改动为零。
- **SC-006**：对中等规模仓库的一次检查在 5 分钟内完成，支持交互式发布前使用。

## 假设 / Assumptions

- 本迭代初始范围面向 Java 业务项目（依据平台的 Java 执行数据采集机制）；其他技术栈在本迭代范围之外。
- 仓库基于 git 并具备分支语义（基准分支与待发布分支共享共同祖先）。
- 判定粒度为"按变更的方法/路由"，报告中呈现行级明细。仅部分执行的单元按变更行/分支粒度报告，暴露未覆盖明细并标记 'partial'（经 /speckit-specify Q1 解决；三色判定语义不变）。
- 本迭代中"拦截"未测试变更是由人依据报告做出的决定；自动化的发布门禁拦截是后续迭代（宪法第六篇章 #5），此处不在范围。
- SC-006 中"中等规模仓库"指约数十万行代码 / 每次发布数千行变更量级；5 分钟目标是交互式使用的默认值（性能强化为最后一个迭代）。
- 系统面向可能没有单元测试的传统业务项目；它不依赖单元测试覆盖率。
